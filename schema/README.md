# Схема и поставочная база

Здесь лежит всё, с чем контроллер приходит к пустому тому postgres: структура, поставочные данные
и архив миграций, которыми эта структура выросла.

Каталог целиком монтируется в postgres как `docker-entrypoint-initdb.d` (стенд —
`deploy/core-infra.env`, переменная `WAF_PG_INITDB`). Postgres читает оттуда **только верхний
уровень и только на пустом томе**; подкаталоги он пропускает — на этом и держится раскладка.

## Что читает postgres

| Файл | Что делает |
| --- | --- |
| `01-baseline.sql` | Структура: таблицы, индексы, ограничения. Машинный `pg_dump` со снимка |
| `02-shipped.sql` | Данные поставки: пространство, справочники, страницы отказа, CRS, `default`-профили, каталог инспекторов, заполненный журнал миграций |
| `03-geo.sh` | Выгрузка MaxMind из `seed/*.sql`, если она есть |

Порядок — по имени, и он существенный: страны из `03-geo.sh` ищут пространство по имени, а его
заводит `02-shipped.sql`.

## Что postgres не читает

| Каталог | Что там |
| --- | --- |
| `migrations/` | Архив из 101 файла — дорога к поставке 1.0. Сюда же ложится всё, что выпущено после неё: `100_*.sql` и дальше |
| `stand/` | Стендовое дерево: серверы, пути, апстримы, списки. Ставится отдельным шагом, клиенту не едет |
| `seed/` | Выгрузки GeoLite2. Не в git: лицензия и размер |
| `build/` | Сборщик поставки |

## Что в поставке

Установка на пустом томе поднимается с одним пространством `default`, справочником типов
содержимого, форматом журнала, обменником тел, каталогом из двенадцати отказов, восемью
страницами отказа и двумя заготовками (виджет капчи, форма входа), двумя пресетами списков
адресов, CRS из двадцати файлов в пяти наборах, каталогом из десяти процессов-инспекторов и
неуничтожимым `default` у каждой подсистемы профилей.

Чего в ней нет: серверов, портов, путей, апстримов, сертификатов, чьих-то списков адресов и
объявлений инспекторов. Пустая установка не слушает ничего — конфигурацию заводит оператор.

Профили `default` приходят ровно такими, какими их считает
[`controller/src/default-profile.ts`](../src/default-profile.ts): панель на свежей установке не
должна говорить «профиль отличается от поставки».

## Миграции после поставки

Поставка 1.0 зафиксирована. Новая правка схемы — новый файл `migrations/1NN_имя.sql`, а не
правка `01-baseline.sql`.

Что уже применено, видно в таблице `waf_schema_log`: она приходит вместе с поставкой, отмеченная
по весь архив. Накатывает недостающее сам контроллер при старте (`src/migrate.ts`, под
`pg_advisory_lock`); `npm run migrate:check` показывает план, ничего не применяя. Предполёт e2e
(`tests/lib/bootstrap.mjs`) пока держит свою копию той же логики. Почему накатчик живёт в
контроллере — `core/migrate/README.md` репозитория `placitum-core`.

## Стенд

`stand/stand.sql` — то, что раньше приезжало сидами 011, 017, 018, 024, 041, 042, 045, 051, 070,
072 и 074: дерево, с которого живёт `deploy/docker-compose.yml`. Кладётся поверх поставки:

```sh
docker compose exec -T postgres psql -U waf -d waf -f /docker-entrypoint-initdb.d/stand/stand.sql
```

Предполёт делает это сам после `--reset-db`. `stand/geo-test.sql` — три выдуманные страны из
архивных `011`/`014`; нужны только базе, которой не досталось выгрузки MaxMind.

## Срезать новую поставку

```sh
node controller/schema/build/baseline.mjs
```

Скрипт поднимает одноразовый postgres, катает на него `migrations/` целиком, режет результат на
поставку и стенд по правилам, описанным в самом скрипте, и переписывает все четыре файла. Нужен
docker; занимает пару минут.

Делать это стоит не после каждой миграции, а когда режется следующая версия продукта: между
версиями установки обновляются файлами из `migrations/`, и обрыв этой дороги обновлением baseline
оставит живые базы без пути вперёд.
